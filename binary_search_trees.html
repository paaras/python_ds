Tree nodes

So far our nodes have had one pointer, next, so a linked list can only go in one direction. A tree node has two pointers, left and right. Each pointer can point to another node, or to None if there's nothing there.

Binary search tree rule

  
A binary search tree keeps its nodes in order. Values smaller than a node go on its left and values bigger than it go on its right. This applies to every node, not only the node at the top, so each side is a smaller tree that follows the same rule. Click any node to check.

  

  







  
Searching a linked list vs a tree

  
To find a value in a linked list we have to check each node starting from the head. In a tree we compare the value with a node and we know which side it has to be on, so we never look at the other side. Both of these hold the same 15 values. Pick a value and press Start.

Searching a tree is binary search

  
Binary search checks the middle of a sorted list and throws away the half the target can't be in. In this tree each node is the middle of the values below it, so every time we go left or right we throw away half of the values, the same as binary search. Step through both and compare.

The Tree class

  

    

      
A LinkedList only needed to remember its head. A Tree only needs to remember the node at the top, called the root, because every other node can be reached from it by going left and right.

      
A new tree doesn't have any nodes yet, so root starts as None.

      

    

    

      

      

    

  







  
Adding a value

  
To add a value we start at the root and compare. If the new value is smaller we go left, and if it's bigger we go right. We keep doing that until we reach an empty spot, and the new node goes there. Try it with the buttons.

Adding a value: code

  
current starts at the root and moves down one level each time through the loop. Before it moves it checks if the next spot is None, because that's where the new node goes. An empty tree has nothing to compare with, so the new node becomes the root.

  

  







  
Finding a value

  
find goes down the tree the same way as add, but it prints each node it visits and stops when it finds the value. If current becomes None we've gone past the bottom of the tree, so the value isn't in it.

  

  







  
Printing every value

  
To print every value we can't follow a single path, we have to visit every node. Each node does three things in order: print everything on its left, print itself, then print everything on its right. Its left side is a smaller tree, so it does the same three things, and so does the left side of that. This is recursion.

  

  

  
Output

  







  
Printing every value: code

  
print_from does those three things for one node. It calls itself on node.left, prints node.value, then calls itself on node.right. The base case is when node is None, since there's nothing to print. Each call waits on the call stack until the call above it finishes, the same way factorial did.

Deleting a value

  
Deleting is harder than adding because the node we remove might have other nodes under it. We can't lose those nodes, so what we do depends on how many children the node has.

  

    
No children
Nothing is under it, so we can remove it.

    
One child
The child moves up into its place. Everything under the child comes with it.

    
Two children
Something has to take its place. The next slide explains which node.

Deleting a node with two children

  
Whatever takes the node's place has to be bigger than everything on its left and smaller than everything on its right, or the tree breaks the rule. If we write the values in sorted order, the value right after the value we're deleting works. In the tree that's the smallest value on the right side, so we go right once and then keep going left until there's no left child.

  
We copy that value into the node we're deleting, then delete the old copy. The old copy can't have a left child, so deleting it is easy.

What delete_from returns

  
When we removed a node from a linked list we needed prev so we could change the node before it. In a tree we would need the parent and whether we came from its left or right. The recursive version gets around this. delete_from returns the node that should be in that spot after the delete, and the parent stores it:

  

  

    
The value is further down
Nothing changes at this node, so it returns the same node.

    
The node has no children
The spot should be empty now, so it returns None.

    
The node has one child
The child should be in the spot now, so it returns the child.

  







  
Deleting a value: code

  
Each call compares the value with node.value and calls itself one level down on the left or right. When it finds the value it checks how many children the node has. On the way back up, each call stores what it got back and returns its own node.

Adding values in sorted order

  
The shape of a tree depends on the order its values were added. If we add them in sorted order, every new value is bigger than everything already in the tree, so it always goes right. We end up with a tree shaped like a linked list, and searching it is as slow as searching a linked list.

Height

  
add, find and delete all follow one path from the root down, so the most checks they can make is the height of the tree. In a full tree each level has twice as many nodes as the level above it, so the number of nodes grows much faster than the height. Time complexity

  
n is the number of values in the tree. A balanced tree has about log n levels because each level doubles the number of nodes, the same way binary search halves the list. A lopsided tree can have n levels if every node is on the same side.

  

    
MethodBalancedLopsidedWhy

    
      
addO(log n)O(n)Follows one path down to an empty spot

      
findO(log n)O(n)Follows one path down until it finds the value or reaches None

      
deleteO(log n)O(n)Follows one path down to the value, and maybe further down to the smallest value on its right

      
printO(n)O(n)Has to visit every node once, whatever shape the tree is

    
  

  
Finding a value in a linked list is always O(n), so a tree is only faster when it stays balanced.







  
Space complexity

  
The tree takes O(n) space because there's one node for every value, and each node stores its value and two pointers. add and find use a loop with one current variable, so they only need O(1) extra space.

  
print and delete use recursion, and every unfinished call takes up space on the call stack. The stack gets as deep as the tree is tall, so it's O(log n) for a balanced tree and O(n) for a lopsided tree.

  

  

    

    
Call stack at the deepest point of print

  







  
Balancing by rebuilding

  
One way to fix a lopsided tree is to rebuild it. First we collect the values in sorted order, using the same order as print. Then the middle value becomes the root, the values before it build the left side, and the values after it build the right side. Each side picks its own middle the same way, so the tree ends up as short as it can be.

  







  
Balancing with rotations

  
Rebuilding takes O(n) because it visits every node, so we don't want to do it after every add. Instead we can fix only the part of the tree that got lopsided with a rotation. The middle node moves up and the node above it moves down to the side. The values are still in order afterwards, so the tree still follows the rule.

  

  

  







  
Self-balancing trees

  
A self-balancing tree does a rotation as soon as part of it gets lopsided. After every add it goes back up the path it took and checks each node. If a node's left or right side is 2 or more levels taller than the other side, it rotates there. This kind of tree is called an AVL tree. Both trees below get the same values in sorted order, which is the worst case for a regular tree.
