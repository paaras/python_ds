Searching a list

A cafe keeps its menu in a list, where each item is a name and a price


  
    
    
  • To find the price of "oat", we have to check each item from index 0 until we reach it
    • 
    
  • "oat" is last, so it takes 7 checks, and a list with n items can take n checks, which makes this search O(n)
    •

Turning a key into a number

  

    

      
An index is a number and a key is text, so the first step is to turn the key into a number

      
    
        
  • Python stores every character as a number, and ord returns that number, so ord("a") is 97 and ord("b") is 98
    • 
        
  • To turn a whole key into one number, we add up the numbers of its letters
    • 
        
  • For "tea" that is 116 + 101 + 97, which is 314
    • 
      

      

      
total starts at 0, and the loop adds the number of each letter in the key

    

    

      

      

      

      

    

  






  
Fitting the number into the list

  

    

      
    
        
  • 314 is too big to be an index in a list of 8 buckets
    • 
        
  • % gives the remainder of a division, and since 314 ÷ 8 is 39 with 2 left over, 314 % 8 is 2
    • 
        
  • A remainder after dividing by 8 is always 0 to 7, so it's always a valid index
    • 
        
  • "tea" gets index 2 every time, which is how we find it again
    • 
      

      

    

    

      

      

      

      

    

  






  
put and get

  

    

      
From here on the menu is a hash table instead of a list, and each bucket stores a pair made of a key (the name) and its value (the price)

      

        
          
put(key, value)Calculates the key's index and stores the pair in that bucket

          
get(key)Calculates the key's index and returns the value in that bucket

        
      

      
Calculating a key's index is called hashing the key

    

    

  






  
Collisions

  

    

      
"pie" and "ham" add up to different numbers, but both leave a remainder of 6

      

        
"pie" → 318 % 8 = 6

        
"ham" → 310 % 8 = 6

      

      
    
        
  • Two keys with the same index is a collision
    • 
        
  • Collisions can't be avoided, because there are endless possible keys and only 8 buckets
    • 
        
  • If "ham" replaced "pie" we would lose the price of pie, so a bucket has to hold more than one pair
    •

Chaining

  

    

      
Chaining makes each bucket a linked list, so it can hold any number of pairs

      
    
        
  • The bucket does the job of head by holding the first node of its list, or None when the list is empty
    • 
        
  • Keys that collide become nodes in the same list
    • 
        
  • To find a key, we go to its bucket and search only that list
    •

get

    2.

remove

  

    

      
remove searches the list with prev one node behind current, and what it does next depends on where the key is

      

    

    

      
Where the key isWhat remove does

      
        
At the head of the listPoints the bucket at current.next

        
Later in the listSets prev.next = current.next

        
Not in the tablePrints a message

      
    

  

  






  
Time complexity

  

    

      
put, get and remove all do the same three steps, where n is the number of keys in the table

      

        
StepTime

        
          
Hash the keyO(1), since it depends on the length of the key and not on n

          
Go to its bucketO(1), since it is a lookup by index

          
Search that bucket's listDepends on its length

        
      

      
With as many buckets as keys, each list has about 1 node, so all three are O(1) on average

Load factor

  

    

      
load factor = keys ÷ buckets

      
    
        
  • The load factor is the average length of a list
    • 
        
  • At 1 or below, the lists are short and the table is fast
    • 
        
  • Every new key raises it, so the table slows down unless it adds buckets
    •

Resizing

  

    

      
put ends by checking if there are more keys than buckets

      

    

    

      
resize does two things

      
    
        
  1. Makes a new list with twice as many buckets
    2. 
        
  2. Puts every key into the new list
    3. 
      

    

  

  






  
Watch Out!

  

    

      
    
        
  • resize has to hash every key again, because % 16 gives most keys a different index than % 8 did
    • 
        
  • If each bucket were copied to the same index, get would look in the new bucket and miss the key
    • 
      

      

      

    

    

      
Resize both ways, then look for "tea"

      

      

    

  






  
The cost of resizing

  

    

      
    
        
  • resize is O(n), since it moves every key
    • 
        
  • Each doubling takes twice as many puts to fill, so resizes happen less and less often
    • 
        
  • 1,000 puts move 1,023 keys in total, which is about 1 extra move per put, so put is still O(1) on average
    •

A better hash function

  

    

      
Adding up letters ignores their order, so "pear" and "reap" always collide. Multiplying the total by 31 before adding each letter fixes that.

      

      

        
KeyAddingMultiplying by 31

        
          
"ab"97 + 98 = 19597 × 31 + 98 = 3,105

          
"ba"98 + 97 = 19598 × 31 + 97 = 3,135

        
      

      
The first letter gets multiplied and the last one doesn't, so the same letters in a different order give a different total

dict and set

  

    

      
Python's dict is a hash table, and a set is a hash table with keys and no values

      
    
        
  • x in my_set is O(1) on average, while x in my_list is O(n) because it searches the list
    • 
        
  • dict hashes keys with Python's built-in hash(), which works on strings, numbers and tuples
    • 
        
  • A list can't be a key because if the list changed, its hash would change and dict would look for it in the wrong bucket
    •

Summary

  

    
StructureSearchAddRemoveSpace

    
      
ListO(n)O(1) at the endO(n)O(n)

      
Linked listO(n)O(1) at the headO(n)O(n)

      
Binary search treeO(log n)O(log n)O(log n)O(n)

      
Hash tableO(1)O(1)O(1)O(n)

    
  

  
    
    
  • The hash table times are averages, and the worst case is O(n)
    • 
    
  • The binary search tree times need a balanced tree
    • 
    
  • A hash table is the fastest way to find something by its key, but it keeps no order, so finding the smallest key means going through the whole table
